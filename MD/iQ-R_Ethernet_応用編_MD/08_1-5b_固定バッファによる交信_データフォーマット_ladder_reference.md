## データフォーマット (原本 p.78)

固定バッファによる交信時に使用するデータフォーマットについて説明します。

通信データは，ヘッダとアプリケーションデータで構成されます。

### ヘッダ (原本 p.78)

ヘッダは，TCP/IP，UDP/IP用ヘッダです。RJ71EN71またはRnENCPU(ネットワーク部)が自動で付加および削除するため，設定する必要はありません。

ヘッダ部の内訳を示します。

 - TCP/IP: イーサネット(14バイト)＋IP(20バイト)＋TCP(20バイト)
 - UDP/IP: イーサネット(14バイト)＋IP(20バイト)＋UDP(8バイト)

### アプリケーションデータ (原本 p.78-79)

交信手段が"固定バッファ (手順なし)"の場合，アプリケーションデータは，下記のデータコードをバイナリコードで表します。交信データコードの設定に関係なく，バイナリコードでの交信が行われます。

テキスト(コマンド): 最大10238バイト

無手順の場合には，手順ありで付加されるサブヘッダやデータ長がないため，データはすべて有効なテキストとして扱われます。また，RJ71EN71およびRnENCPU(ネットワーク部)は，受信した伝文(パケット)のサイズを受信データ長格納エリアに格納してから固定バッファ受信状態信号をONします。受信側でアプリケーションデータのバイト数やデータ種別などが分かるように，伝文のアプリケーションデータ中にデータ長やデータ種別コードなどを含めるなどのチェック手段を設けられることを推奨します。

交信手段が"固定バッファ (手順あり)"の場合のアプリケーションデータの構成を示します。

### フォーマット (原本 p.79)

#### バイナリコードでの交信時

【図】バイナリコード交信のアプリケーションデータ構成(原本 p.79)

コマンド伝文(交信要求元側): サブヘッダ(2バイト、L→H) → データ長設定(2バイト、L→H) → テキスト(コマンド)(最大5113ワード)

レスポンス(交信要求先側): サブヘッダ(1バイト) → 終了コード(1バイト)

#### ASCIIコードでの交信時

【図】ASCIIコード交信のアプリケーションデータ構成(原本 p.79)

コマンド伝文(交信要求元側): サブヘッダ(4バイト、H→L) → データ長設定(4バイト、H→L) → テキスト(コマンド)(最大5112ワード)

レスポンス(交信要求先側): サブヘッダ(2バイト、H→L) → 終了コード(2バイト、H→L)

## サブヘッダ (原本 p.80)

サブヘッダは，RJ71EN71またはRnENCPU(ネットワーク部)が自動で付加および削除するため，設定する必要はありません。

| データフォーマット | コマンド(相手機器→RJ71EN71またはRnENCPU(ネットワーク部)) | レスポンス(RJ71EN71またはRnENCPU(ネットワーク部)→相手機器) |
|---|---|---|
| バイナリコード | ビットパターン `0 1 1 0 0 0 0 0`(b7〜b0) = 60H 00H(サブヘッダ) | ビットパターン `1 1 1 0 0 0 0 0`(b7〜b0) = E0H(サブヘッダ) |
| ASCIIコード | ビットパターン `0 1 1 0 0 0 0 0`(b7〜b0)。"6"↔6H，"0"↔0H。バイト列: 36H 30H 30H 30H(サブヘッダ) | ビットパターン `1 1 1 0 0 0 0 0`(b7〜b0)。"E"↔EH，"0"↔0H。バイト列: 45H 30H(サブヘッダ) |

## データ長設定 (原本 p.80)

テキスト(コマンド)部のデータ容量を示します。

 - バイナリコードでの交信時: 最大5113ワード
 - ASCIIコードでの交信時: 最大2556ワード

## テキスト(コマンド) (原本 p.81)

コマンド/レスポンスのフォーマットを示します。

### バイナリコードでの交信時

【図】バイナリコード時のコマンドフォーマット(原本 p.81)

コマンドフォーマット: サブヘッダ(60H 00H) → データ長設定(L)(H) → 送受信データ(最大5113ワード分、各1ワード(2バイト)、(L)(H)の順)

送信/受信命令のデータ指定/格納デバイスは、先頭デバイスをn とすると: n=データ長設定、n+1〜n+設定データ長=送受信データ(各(H)(L)の2バイト構成)。

### ASCIIコードでの交信時

【図】ASCIIコード時のコマンドフォーマット(原本 p.81)

コマンドフォーマット: サブヘッダ(36H 30H 30H 30H) → データ長設定((H)…(L)) → 送受信データ(最大5112ワード分)。ASCII-バイナリ変換を介して、先頭デバイスnからn+1〜n+設定データ長(各(H)(L)の2バイト構成、最大2556ワード分)に格納される。

## 終了コード (原本 p.82)

レスポンスに付加される終了コードには，エラーコードが格納されます。(456ページ データ交信で相手機器に返される終了コード)

また，終了コードは，BUFSND命令，BUFRCV命令の完了ステータスエリア(コントロールデータ内)にも格納されます。

固定バッファ交信を実施しているにもかかわらず，SLMPによる交信やランダムアクセス用バッファによる交信のエラーコードが格納された場合，下記の可能性があります。

| 内容 | 処置方法 |
|---|---|
| 相手機器からRJ71EN71またはRnENCPU(ネットワーク部)へ送信する伝文のアプリケーションデータ部の中に指定するデータ長とテキスト部分の実際のデータサイズが異なっている。 | アプリケーションデータ部の中に指定するデータ長は，テキスト部分の実際のデータサイズを指定してください。(下記の内容を参照してください) |
| 相手機器からRJ71EN71またはRnENCPU(ネットワーク部)へ送信する伝文のサブヘッダが誤っている。 | アプリケーションデータ部の中に指定するサブヘッダを見直してください。 |

交信データは，自局や相手局のバッファの制限により，データが分割されて交信されることがあります。分割して受信したデータをRJ71EN71およびRnENCPU(ネットワーク部)で復元(再組立て)して交信します。(受信したデータの復元(再組立て)は，交信データ内のデータ長をもとに行います)交信データ内のデータが正しくないときのRJ71EN71およびRnENCPU(ネットワーク部)の処理を示します。

| 交信手段 | 処理内容 |
|---|---|
| 固定バッファ (手順あり)，ランダムアクセスバッファ | サブヘッダの直後に指定するデータ長＜テキストのデータ量のとき: サブヘッダの直後に指定するデータ長分のテキストの直後からのデータを2つ目の伝文と見なします。各伝文の先頭がサブヘッダとなるため，RJ71EN71およびRnENCPU(ネットワーク部)はサブヘッダのコードにより対応する処理を行います。RJ71EN71およびRnENCPU(ネットワーク部)が扱うコード以外のサブヘッダであれば，異常完了のレスポンスを相手機器へ送信します。上記の場合，レスポンスは，サブヘッダとして処理したコードの最上位ビットを1にしたコードを返します。例えば，コマンドのサブヘッダ部が65Hであった場合，レスポンスのサブヘッダはE5Hになります。／サブヘッダの直後に指定するデータ長＞テキストのデータ量のとき: RJ71EN71およびRnENCPU(ネットワーク部)は，不足分の残りのデータの受信を待ちます。レスポンス監視タイマ値以内に残りのデータを受信できたとき，RJ71EN71およびRnENCPU(ネットワーク部)はサブヘッダのコードにより対応する処理を行います。レスポンス監視タイマ値以内に残りのデータを受信できなかったとき，RJ71EN71およびRnENCPU(ネットワーク部)は次の処理を行います。・相手機器へABORT(RST)命令を送信して回線をクローズします。・'コネクション別状態エリア'(Un\G100~Un\G163)にエラーコードを格納します。 |
| 固定バッファ (手順なし) | 無手順には，伝文データ長がないため，受信したデータはそのまま受信バッファエリアへ格納されます。受信側でアプリケーションデータのバイト数やデータ種別などが分かるように伝文のアプリケーションデータ中にデータ長やデータ種別コードなどを含めるなどのチェック手段を設けられることを推奨します。 |

【図】データ分割時のサブヘッダ判定(原本 p.82)。相手機器が送ったデータ(サブヘッダ＋連続データ)を、RJ71EN71またはRnENCPU(ネットワーク部)が第1データと第2データに分割して判断する。第2データの先頭部分を新たなサブヘッダとして処理する。
